# nav_markers — навигация БПЛА на складе по статическим реперным маркерам (ArUco)

Новая тема ВКР: **«Навигация беспилотного летательного аппарата на складе по статическим реперным маркерам
(ArUco и др.) для автономной инвентаризации»**. Обоснование — документ «Изменение вектора развития».
Папка самостоятельная: файлы INVENT_DRONE не меняются, модели склада и камеры (`core/invent_core`)
и генераторы симуляции (`sim/`) только импортируются.

## Идея в одном абзаце

Склад статичен, его план известен — строить карту на лету (SLAM) не нужно, а визуальная одометрия у близких
стеллажей на 1–1,5 м/с страдает от смаза. Поэтому два слоя: **абсолютный** — ArUco-метки с известными
координатами (каждая даёт позу без накопления ошибки), **относительный** — IMU + оптический поток вниз +
дальномер, который держит позу между метками. Оба соединяет EKF2 автопилота PX4; узел меток передаёт
ему позу каждого кадра как «внешнее зрение».

## Результат в SITL (PX4 v1.17 + Gazebo Harmonic, прогон 11 от 12.10.2026)

Задание: взлёт с дока → проход 1 → захват ячейки B-05-2-2 (ярус 2) → магистраль → проход 2 → захват C-03-1-1
(ярус 1) → посадка на док. Путь 62 м, полёт 77 с, скорость в проходе 1,5 м/с, метки 20 см (4×4) через 2 секции
в шахматном порядке на высотах 0,5 / 1,5 / 2,3 м, камеры меток 640×480 при 5 Гц.

| Метрика | Значение |
|---|---|
| Задание | выполнено целиком: 22 точки, 2 захвата из 2, без поиска метки и аварий |
| Покрытие метками | 96 % времени полёта, самый длинный пропуск 1,7 с |
| Ошибка EKF2 по горизонтали | RMSE 7,8 см, 95 % — 15,9 см, максимум 37 см |
| Ошибка позы по меткам по горизонтали | RMSE 5,0 см, 95 % — 8,9 см; ковариация честная (NEES 0,9) |
| Захват ячейки, по горизонтали | 10,3 см и 5,9 см (KPI — 10 см: одна ячейка на границе) |
| Задержка «кадр → поза» | 20 мс (время симуляции) |

Ошибка 15–25 см остаётся в моменты, когда меток в кадре нет дольше секунды (разгоны, смена высоты у ячейки):
дальше EKF2 держится на потоке, а его дрейф в симуляции ~8 % пути. Это прямо подтверждает расчёт шага меток
(документ, разд. 6.1): при k ≈ 8 % для допуска 10 см метки нужны не реже чем через ~1 м пути у ячейки.

## Что где

| Путь | Что делает |
|---|---|
| `nav_core/markers.py` | карта меток: якоря на торцах рядов (уникальные ID), путевые метки на стойках в шахматном порядке (ID повторяются по проходам) |
| `nav_core/aruco_pose.py` | детектор (OpenCV 4.6 и ≥4.7), поправка смещения углов, PnP одной метки (SQPnP), выбор метки при повторе ID по χ², совместная поза по всем углам всех камер (Гаусс–Ньютон, ковариация из якобиана) |
| `nav_core/route.py` | граф проходов, маршрут Дейкстрой, три уровня: склад → проход → ячейка |
| `tests/` | 12 тестов ядра на синтетике (NEES ≈ 4 на 4 ст. св. — ковариация честная) |
| `gazebo/make_world.py` | мир Gazebo = склад INVENT_DRONE + метки + пол с текстурой + плагин потока PX4 |
| `gazebo/make_drone.py` | модель `x500_nav` = PX4 `x500_flow` (поток + дальномер) + 3 камеры меток |
| `gazebo/check_marker_texture.py` | проверка рендером, что метка в Gazebo лежит так, как в карте; калибровка смещения углов |
| `gazebo/run_nav_sitl.sh` | сквозной прогон: мир → PX4 SITL → узлы → задание → метрики |
| `gazebo/eval_nav.py` | метрики прогона и график `track.png` |
| `patches/px4_optical_flow_ringbuffer.patch` | исправление зависания PX4 v1.17 с оптическим потоком (см. ниже) |
| `ros2_ws/src/nav_markers_ros` | узлы `marker_localizer` (метки → EKF2), `nav_mission` (задание), `nav_logger` (журнал) |

## Запуск

Тесты ядра (Windows или Linux):

```bash
.venv/Scripts/python -m unittest discover -s nav_markers/tests
```

Симуляция (WSL Ubuntu 24.04, окружение как для `scripts/smoke_sitl.sh` INVENT_DRONE). Один раз:

```bash
python3 -m pip install --target ~/nav_pylib --no-deps opencv-python-headless==4.10.0.84
```

```bash
cd ~/src/PX4-Autopilot && git apply ~/INVENT_DRONE/nav_markers/patches/px4_optical_flow_ringbuffer.patch && make px4_sitl
```

Прогон (`GPU=1` — рендер на видеокарте через Mesa d3d12; без него WSL рендерит программно и медленно):

```bash
GPU=1 bash nav_markers/gazebo/run_nav_sitl.sh
```

Параметры — переменными окружения: `TARGETS="B-05-2-2,C-03-1-1"` (ячейки задания), `V_AISLE=1.5` (скорость
в проходе), `STEP_BAYS=2` (шаг путевых меток, секций), `HEIGHTS="0.5 1.5 2.3"` (высоты рядов меток),
`CAM_RATE=5` (Гц камер меток), `GUI=1`. Результат — `nav_markers/runs/<время>/`: `summary.txt`, `track.png`,
`track.csv`, `fixes.csv`, `events.csv`, `status.jsonl`, логи PX4 и ROS.

## Настройки PX4 (задаются скриптом до старта, через `PX4_PARAM_*`)

| Параметр | Значение | Зачем |
|---|---|---|
| airframe | 4021 `gz_x500_flow` | поток вниз + дальномер LW20, GPS выключен |

Плюс параметры полёта в помещении из `sim/px4_params_indoor.txt` INVENT_DRONE (скорости, аварийные режимы).

## Что найдено по дороге

Каждый пункт — проверен в коде или прогоне, ссылки на прогоны — `nav_markers/runs/`.

**PX4 и симулятор**
- **PX4 v1.17 с `x500_flow` не взлетает вообще**: `VehicleOpticalFlow::Run` зацикливается в
  `RingBuffer::pop_oldest` на первом сообщении потока (`timestamp_oldest = 0`, пустые записи с `time_us = 0`
  проходят проверку). Очередь `wq:nav_and_controllers` встаёт — `sensors`, EKF2 и регуляторы не работают.
  Найдено стеком потока в gdb; исправление — одна строка (`patches/`), накладывается обратимо (`git apply -R`).
- **Плагин потока PX4 нужно подключать в мире явно**: мир со своим списком плагинов отключает `server.config`.
- **Однотонный пол не даёт потоку точек** — пол с «бетонной» текстурой (`--floor-texture-mm 0` — проверить без
  неё; это и есть довод про гладкий бетон).
- **Скорость симуляции**: три камеры 800×600 при 15 Гц + тени + программный рендер — 0,02 реального времени.
  Без теней, 640×480 при 5 Гц и рендер на видеокарте (`GPU=1`) — 0,2–1,0.
- **Кадр камеры Gazebo рендерится (и пишется `<save>`) только при подписчике на её топик** (gz-sim 8.15).
- **Истина Gazebo — начало модели, а EKF2 — `base_link`**, он на 0,24 м выше (поза `x500_base` переносится
  на звенья при `merge='true'`); по горизонтали совпадают. Учтено в `eval_nav.py`.

**Метки и поза**
- **OpenCV 4.6 (Ubuntu 24.04) не находит половину меток на рендере Gazebo**, 4.10 находит все — для узлов
  ставится отдельно в `~/nav_pylib`, система не меняется.
- **IPPE_SQUARE в OpenCV 4.13/5.0 врёт на точных данных** (~1 px, ~1 см), когда метка видна почти в лоб —
  обычный ракурс боковой камеры. Используется SQPnP.
- **Курс по одной метке ненадёжен**: при фокусе 320 px ошибка 7–25° (документ, разд. 5.3, подтверждено).
  Курс уточняется совместно по всем меткам кадра: две метки по разные стороны прохода дают 0,01–0,2°.
- **Найденные углы смещены внутрь метки на ~0,48 px** (метод SUBPIX; NONE/CONTOUR — 0,67, APRILTAG — 0,42
  с большим разбросом). Без поправки дальность завышена на 1,5–2,3 %, а курс по двум якорям — на ~1,3°
  (→ 5–7 см сбоку). Поправка `corner_bias_px` калибруется `check_marker_texture.py` — на реальной камере так же.
- **Граница Крамера–Рао слишком оптимистична** для реальной ошибки (NEES 57): остаётся систематика. С нижней
  границей σ = 3 см ковариация честная (NEES 0,9).
- **Якоря на 1,5 м не видны с дока на земле** (за верхним краем кадра) — опущены до 1,0 м.

**EKF2 и метки (важно для главы о слиянии)**
- **EKF2 считает внешнее зрение «прерывистым», если сообщений нет дольше ~0,4 с**, выключает его и при
  возобновлении сбрасывает позицию на первое измерение (89 сбросов за полёт, прогон 5). Сброс на точную позу по
  метке безопасен; опасен сброс на неточную — поэтому важна честная ковариация.
- **Свой фильтр «скорость EKF2 → поза → EKF2» нельзя**: пробовали непрерывно отдавать в EKF2 позу фильтра,
  прогнозируемую по скорости самого EKF2 (прогоны 6–10). Это петля обратной связи без независимого измерения:
  поза фильтра подтягивает скорость EKF2, фильтр интегрирует подтянутую скорость — оценка уходила на метры,
  а метки потом отвергались как «несогласованные». Корректная версия требует сырой скорости потока, которой нет
  в мосте uXRCE-DDS по умолчанию. Оставлена прямая схема: каждая поза по меткам — отдельное измерение EKF2.

## Что дальше

1. **Главный эксперимент ВКР** (документ, разд. 10): серия прогонов `STEP_BAYS` = 1 / 2 / 3 / 10 ×
   `V_AISLE` = 0,5 / 1,0 / 1,5 — ошибка навигации от шага меток и скорости; по 3 прогона на точку.
2. **Захват ячейки ≤ 10 см стабильно**: метки на уровне каждого яруса у фасада и захват по усреднённой позе
   за удержание, а не по последнему кадру.
3. Сырая скорость потока (`vehicle_optical_flow_vel`) в мост DDS — тогда можно вернуть свой фильтр между метками.
