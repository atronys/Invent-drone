## 1. Gao & Zhang — «Introduction to Visual SLAM»

**Что это.** Учебник с кодом: от линейной алгебры до собственного stereo VO. Сильная сторона —
каждая глава заканчивается практикой на C++ (Eigen, Sophus, OpenCV, Ceres, g2o, DBoW3, PCL, OctoMap).

**Слабое место для нас:** книга под Ubuntu 18.04; на 24.04 код `slambook2` ломается на версиях
Sophus/fmt/g2o/Pangolin. Решение — Docker ([docker/slambook](../docker/slambook/Dockerfile), задача ENV-05).
И второе: **книга учит понимать SLAM, а не делать продукт** — свой SLAM для продукта не пишем, берём
готовый VIO (см. ADR-5 в [02_architecture.md](02_architecture.md)).

## 2. Статья A — Lin, Chang, Huang, *Drones* 2024

### Суть
Две части: (1) **локализация и навигация** дрона в помещении — сравнение UWB, QVIO, AprilTag,
RTAB-Map; навигация через ROS Navigation Stack (глобальный navfn/Дейкстра + локальный DWA);
PX4 + MAVROS + QGroundControl; (2) **инвентаризация** — обучение с подкреплением (Actor-Critic и PPO)
выбирает перемещения/поворот камеры, чтобы увидеть максимум меток за минимум шагов.

### Стенд и цифры
- Помещение 8×7×2.5 м, AprilTag tag36h11 на потолке, 4 UWB-якоря; дрон ModalAI M500 (PX4,
  Snapdragon 821), RealSense D435 + UP Squared; тяжёлые вычисления — **на ноутбуке по WLAN**
  (бортовой компьютер не справился), обучение — RTX 3070 Ti / 4090.
- RL: признаки ResNet34 → policy/critic; действия — 8 перемещений по 1 м и поворот камеры
  −40…+40° с шагом 10°; награда — за **новые** метки (каждая засчитывается один раз), штраф за шаги
  без новых меток, бонус за полный обход; YOLOv5 + K-means — «направляющий механизм» к зонам
  с кандидатами. Симуляция — UE4 + AirSim, навигация — Gazebo.
- Гиперпараметры: PPO lr 0.02, ≤50 шагов, ε = 0.2, обновление каждые 20 эпизодов;
  AC lr 2·10⁻⁴, γ = 0.9, ≤100 шагов.
- Результаты: симуляция (26 коробок) — PPO **94.62%**, AC 90.38%;
  «реальность» (16 коробок) — PPO **99.38% за 16.2 шага**, AC 98.13% за 36.4 шага.
- Код: `github.com/kellen080/Navigation`, `github.com/kellen080/Indoor_Positioning` (ROS 1).

### Что берём (правила для нашего проекта)
1. **AprilTag — самая стабильная глобальная коррекция**, две и более метки в кадре точнее одной →
   в MVP ставим маркеры на торцах рядов/входах в проходы (LOC-06).
2. **UWB не дрейфует по XY, но шумит по Z и чувствителен к препятствиям** → на складе
   металлические стеллажи = многолучёвость; UWB не основной источник (максимум эксперимент LOC-10).
3. **VIO нужна текстура; быстрый разворот на месте рвёт одометрию** (сценарий 4) → ограничение
   скорости рыскания заложено в `coverage.ScanParams.yaw_rate_deg` и в `mission_node`.
4. **RTAB-Map в режиме локализации полезен там, где VO расходится** (большие пространства) — но на
   складе одинаковые проходы → риск ложных замыканий; только с проверкой (LEARN-10).
5. **Вычисления по Wi-Fi — плохая идея на складе** (радиотени от стеллажей) → вся автономия на
   борту, по сети только данные.
6. **2D-навигация на фиксированной высоте** — ограничение, которое авторы сами называют
   → у нас структурированный 3D-маршрут по плану склада (ADR-6).
7. **Разделять детекцию и декодирование**: детектор находит кандидатов этикеток, декодер читает;
   кандидат без чтения = повод для перескана (статус `UNREADABLE`, задача PER-09).
8. Методология: симуляция → реальный стенд, 10 прогонов, метрики «доля найденного» и «шаги/время» —
   переносим в протокол экспериментов диплома (THESIS-06).

### Критика (не копировать в диплом, превратить в новизну)
- В тексте PPO назван off-policy, а DQN — on-policy; общепринято **наоборот** (PPO — on-policy,
  DQN — off-policy).
- «Реальный» тест RL — **не полёт**: камера на мобильной платформе, 3×12 точек × 9 ракурсов = 324
  заранее снятых кадра; агент «ходит» по базе кадров.
- **AprilTag на коробках вместо линейных штрихкодов** (GS1-128/Code128 на паллетных этикетках) —
  задача чтения на порядок проще реальной (см. расчёт оптики в 02_architecture.md §6).
- Масштаб 3.6 м прохода и 16 коробок; нет высоких стеллажей, людей, погрузчиков, ночного света.
- Каждый пункт = направление, где твоя работа может быть сильнее: реальные этикетки, реальная
  высота, реальный полёт, атрибуция к адресу ячейки, сверка с WMS.

## 3. Статья V — Zhang et al., *Scientific Reports* 2025

### Суть
Robot Mobile Fulfillment System (роботы возят стеллажи к станциям отбора, как Kiva/Amazon):
заказы приходят в реальном времени, нужно выбрать стеллажи и спланировать пути. Предложены:
JOTP — эвристика с совместным индикатором «соответствие стеллажа заказу + стоимость пути»
(w₁ = w₂ = 0.5); JOTP-RL — POMDP, мультиагентное RL QMIX (централизованное обучение,
децентрализованное исполнение); улучшенный THA* — пути с учётом **заторов** и без лишних
вычислений. Доказана NP-трудность пакетной задачи сведением к **взвешенному покрытию множеств**.
Эксперименты: синтетические наборы Syn-A/Syn-B; базовые методы LEF, ILP, ALNS, ATP; метрики —
makespan и суммарная стоимость пути. Параметры обучения: 5000 эпох, batch 32, γ = 0.999,
lr = 5·10⁻⁴, буфер 5000.

### Что берём
1. **Формализм постановки** (Определения: Order, Rack, Robot, Workstation) → шаблон главы 2
   диплома: Location, Pallet, Drone, Dock, Mission, Sortie (LEARN-17).
2. **Порог заряда с гарантией достижимости зарядки** → уже реализовано в планировщике вылетов
   (`coverage.plan`: резерв АКБ + обязательный возврат к доку).
3. **NP-трудность через сведение** → наша задача выбора пролётов при ограничении энергии —
   orienteering problem; это обосновывает эвристику и сравнение с базовыми методами (MIS-07).
4. **Заторы** → на реальном складе проходы заняты погрузчиками: планировать облёт по «окнам»
   доступности (WMS знает, где идут задания) — продуктовая фича «WMS-aware scheduling» (MIS-06).
5. **QMIX/CTDE** — задел для флота из нескольких дронов (MIS-09, вне MVP).
6. **Методология**: синтетические наборы + несколько базовых методов + две метрики — повторить
   для планировщика.

### Ограничения
Не про инвентаризацию и не про дроны; только синтетика на сетке; нет физики и энергии полёта.
Поэтому для MVP — второстепенна, для диплома — полезна как образец строгости.

## 4. Статья M — Multilayer Mapping Kit, *IEEE Access* 2021

### Суть
Трёхслойная карта для навигации БПЛА на слабом бортовом компьютере:
**awareness** (цилиндрические координаты, привязана к телу, raycasting сводится к 2D в плоскости ρ–z),
**local** (вероятностная воксельная карта, log-odds с насыщением),
**global** (динамическая память: подкарты 5×5 / 5×5×5, вне активной зоны хранятся только занятые
воксели). Три потока (awareness, local-global, визуализация — на наземной станции). Выходы:
2D-сетка, глобальная карта, локальная ESDF для планировщиков.

### Цифры
Карта 50×50×5 м при вокселе 0.2 м и 64 Б/воксель ≈ 100 МБ. Для незанятых измерений
P = 0.4, logit = −0.4 (подходит и для depth-камер, и для лидара).

### Что берём
1. **Log-odds с насыщением** → карта быстро «забывает» уехавший погрузчик или ушедшего человека.
2. **Не держать плотную глобальную карту на борту**: склад 100×60×12 м при 0.2 м ≈ 9 млн вокселей
   ≈ 0.6 ГБ. Глобальная геометрия у нас уже есть — из плана склада (`layout`); на борту — только
   локальная карта вокруг дрона.
3. Визуализация — на наземной станции, не на борту.
4. MLMapping — ROS 1; для ROS 2 — OctoMap или nvblox (если Jetson). Для MVP хватит
   «пузыря безопасности» по depth-кадру (SAFE-01), полноценная карта — Ф4.
